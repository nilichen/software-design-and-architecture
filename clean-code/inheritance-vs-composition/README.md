# Clean Code | Inheritance vs Composition

This folder is the app after the fixes. **[See before vs after as one diff](https://github.com/nilichen/software-design-and-architecture/commit/97abaf5d4ad38674a95bc59e3efe897ed5e64542)** (switch to *Split* for side by side), or [browse the before](https://github.com/nilichen/software-design-and-architecture/tree/70524411cc8f96ee60d2e7c2c71cae4bd49044e2/clean-code/inheritance-vs-composition).

In the notes below, `before/x.py` means `x.py` in the before version and `after/x.py` the file as it is now. To run the before locally: `git switch --detach 7052441`, then `git switch main` to come back.

## What changed

- **The `isinstance` chains in `desk.py` are gone.** `licence_ok` and `deposit` are now methods on each vehicle in `vehicles.py`, and `book` just calls them (polymorphism). In before/, `deposit()` had no branch for vans, so a van fell through to the bike's deposit of 50.00. In after/, `Van` has its own `deposit()` and the van deposit is 400.00. **Changed output:** VN-321 deposit 50.00 → 400.00.
- **The truck's road toll is charged once.** In before/, `Truck.reserve` added the toll on top of `Vehicle.reserve`. Then someone changed the parent to multiply `daily_price()`, which `Truck` overrides to include the toll, so the toll was counted twice (fragile base class). In after/, `vehicles.py` has no `reserve` or `daily_price`, and the toll is a `RoadToll` part in `pricing.py`. **Changed output:** TR-789 total 260.00 → 220.00.
- **Inheritance is one level, used for an abstraction.** `Vehicle` in before/ was a concrete parent whose methods every child depended on. `MotorVehicle` in after/ is a small ABC: it shares the fields and `refuel`, and its abstract `licence_ok` and `deposit` make Python refuse to create a vehicle that forgets one. `Bike` doesn't inherit from it, because it shares nothing with it.
- **Protocols sit next to the code that uses them.** `Handover` and `Fuelable` in `desk.py` and `PriceComponent` in `rental.py` are Protocols. `vehicles.py` and `pricing.py` import none of them and still fit, because a Protocol only checks the shape of a class. The ABC stays where classes share code, and the Protocols stay where the only question is "what can this object do?".
- **The fat interface is split.** In before/, every `Vehicle` had `refuel`, so `Bike.refuel` had to raise, and `return_vehicle` needed an `isinstance` check on bikes to avoid calling it. In after/, `return_vehicle` asks only for a `Fuelable`, and `Bike` has no `refuel` at all. A type checker rejects a bike sent to the fuel desk before the code runs (interface segregation).
- **The add-on mixins and combination classes are replaced by composition.** `pricing.py` in before/ had three mixins that each hooked `daily_price` through `super()`, plus one class per vehicle and add-on combination. `InsuredVan(Van, InsuranceMixin)` listed its bases in the wrong order, so the method resolution order reached `Vehicle.daily_price` first and silently dropped the insurance. In after/, a `Rental` in the new `rental.py` holds a list of parts (`DailyRate`, `Insurance`, `Gps`, `ChildSeat`, `RoadToll`) and adds up their prices. A new add-on is one class, and `main.py` adds the child seat to a rental while the program runs. **Changed output:** VN-321 total 140.00 → 170.00.
- **`main.py` is the one place that knows the concrete classes and prices.** It builds the vehicles and price parts and hands them to `book` (dependency injection). `desk.py` and `rental.py` depend only on Protocols, so changing a price or giving every truck a GPS means editing `main.py` and nothing else.
- **A stand-in makes the rental easy to test.** `tests/test_rental.py` checks that `Rental.total` adds up its parts using a `Fixed` stand-in part, so no real price list is needed, and it checks `Insurance` on its own. The mixins in before/ could only be tested inside a host vehicle class. Run with `uvx pytest` from after/. `pyproject.toml` only puts after/ on the test import path.
